# 05. Собственный ассемблер

Стенд пятой статьи. Отвечает на обещание, напечатанное в конце четвёртой: как
из строчки `addi sp, sp, -16` получаются те самые 4 байта `ff010113`.

Ассемблер собирает **первую программу серии** и выдаёт байты, совпадающие с
выводом настоящего тулчейна. Не «похожие», а совпадающие: проверяется `cmp`.

## Быстрая проверка

```
source ../../scripts/env.sh

make promise    # обещанное: addi sp, sp, -16 -> байты, двумя ассемблерами
make compare    # вся первая программа: наши байты против настоящих
make run        # запускаем в QEMU то, что собрали МЫ
make where      # один объектный файл, две сборки: кто дописывает la
make listing    # что во что превратилось, строка за строкой
make pseudo     # доля псевдоинструкций по всем программам репозитория
make x86        # тот же скелет на x86: сколько там выдумки
```

## Что показывает каждая цель

**`make promise`.** То, ради чего статья и пишется:

```
настоящий ассемблер:
   0:	ff010113          	addi	sp,sp,-16
  байты в файле:  13 01 01 ff
наш ассемблер:
  байты в файле:  13 01 01 ff
  совпало
```

Обратите внимание на порядок. `ff010113` это СЛОВО, как его печатает
дизассемблер. В файле те же четыре байта лежат наоборот: `13 01 01 ff`.

**`make compare`.** Первая программа серии, 63 байта: 40 кода и 23 строка.
Наш ассемблер и настоящий дают один и тот же образ.

**`make run`.** Проверка, без которой предыдущая ничего не стоит. Правильные
байты на бумаге и работающая программа это разные утверждения. Грузим наш
образ прямо по `0x80000000` и ждём «Привет, мир!».

**`make where`.** Опыт с одним изменяемым параметром. Объектный файл
собирается ОДИН раз, его контрольная сумма печатается до и после. Дальше он
ссылается двумя скриптами, отличающимися ровно одним: куда положить строку.

```
-- .rodata сразу за кодом:   addi t1,t1,36    # 80000028 <message>
-- .rodata по 0x80001000:    addi t1,t1,-4    # 80001000 <message>
-- в самом объектном файле:  addi x6,x6,0
```

Байты разные, объектный файл тот же. Значит ассемблер их знать не мог, и
дописал их компоновщик. Причём обе инструкции пары: `auipc` тоже меняется,
`0x0` против `0x1`.

**`make pseudo`.** Опыт на опровержение. Спина статьи держится на том, что
изрядная часть строк это не инструкции, а выдумка ассемблера. Очевидное
возражение: «вы посчитали по одной удобной программе». Считаем по всем:
26 файлов, 1335 инструкций, псевдо 44%, разброс от 26% до 82%.

## Что умеет ассемблер

Настоящие инструкции RV32I: `lui`, `auipc`, `jal`, `jalr`, ветвления,
загрузки и записи, арифметика с константой и между регистрами, сдвиги,
`wfi`, `ecall`, `ebreak`.

Псевдоинструкции, то есть то, чего в процессоре нет: `li`, `la`, `mv`, `j`,
`jr`, `ret`, `nop`, `beqz`, `bnez`.

Директивы: `.section`, `.globl`, `.string`, `.byte`, `.word`, `.space`.

## Чего он НЕ умеет, и это важнее списка умений

**Не выдаёт объектный файл.** Только плоский образ по заранее известному
адресу. Отсюда следует главное различие с настоящим тулчейном.

Настоящий ассемблер физически не может дописать `la` до конца: он не знает,
куда компоновщик положит метку. В объектном файле на этом месте стоит
`addi x6, x6, 0`, а настоящее смещение подставляется позже. Проверить можно
так:

```
riscv-none-elf-as -march=rv32i -mabi=ilp32 -o h.o ../01-hello/boot.s
riscv-none-elf-objdump -d -M no-aliases h.o | head -8
```

Наш дописывает, потому что сразу пишет образ по `0x80000000` и знает все
адреса. **Это разница не в качестве, а в задаче.** Мы не умнее, мы решаем
задачу попроще.

**Не умеет сжатое расширение C**, макросы, `.align`, выражения в операндах,
секции кроме `.text` и `.rodata`, внешние символы. Всё это в наших программах
не встречается, и добавлять их «на всякий случай» значит писать код, который
никто не проверял.

## Устройство

Два прохода. Первый считает адреса и собирает метки, второй кодирует. Второй
нужен потому, что переход вперёд ссылается на метку, которой на момент первой
встречи ещё нет.

Длина каждой строки известна уже на первом проходе. Единственная
псевдоинструкция переменной длины это `li`: константа маленькая, хватит
одного `addi`; ровная, хватит одного `lui`; иначе `lui` плюс `addi`. Константа
записана прямо в строке, поэтому длина считается сразу.

Чтобы это не разъехалось молча, второй проход сверяет: если насчитанная длина
не совпала с фактической, сборка падает с указанием строки.

## Что здесь лежит

| Файл | Что делает |
|---|---|
| `asm.py` | ассемблер, два прохода, плоский образ |
| `count-pseudo.py` | доля псевдоинструкций по программам репозитория |
| `link-shift.ld` | скрипт с `.rodata` по явному адресу, для `make where` |
| `x86-hello.s` | тот же скелет на x86-64, для `make x86` |
| `Makefile` | цели выше |

## `make x86`: чьё свойство эти 44 процента

Тот же скелет на x86-64, и считаем не инструкции, а мнемоники: сколько строк
из написанных процессор выполняет как есть.

```
-- мнемоники, которые я написал:  lea mov movzbl test je mov inc jmp ret nop
-- мнемоники, которые вышли:      lea mov movzbl test je mov inc jmp ret nop nop nop

СОВПАЛИ ВСЕ 10: каждая написанная мнемоника осталась собой,
ни одна не развернулась в две. Псевдоинструкций тут нет.

Плюс 2 лишних в хвосте. Это НЕ развёртка, а выравнивание секции.
```

Два лишних `nop` цель называет своим именем и не выдаёт за развёртку: `.text`
там `0x20` при выравнивании 16, ассемблер добил секцию до границы. Сверка
сначала честно показала расхождение, и это правильно: пусть лучше кричит, чем
молчит.

Нужен родной x86-ассемблер. На этой машине нашёлся в mingw, на Linux он есть
всегда. Нет его, цель скажет об этом и ничего не сделает.
